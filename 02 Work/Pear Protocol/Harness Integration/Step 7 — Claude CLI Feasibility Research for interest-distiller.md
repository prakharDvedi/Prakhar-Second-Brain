## Trigger for the swap question — a real, code-confirmed quality gap

`apps/agent/src/ai/background/interest-distiller.agent.ts`'s `normalizeInterests()` (lines 196–248) has a deterministic backstop, `isStyleTopic()` (imported from `apps/agent/src/signals/statement-quality.ts:93-105`), that drops any interest tag matching a style/methodology denylist (`scalping`, `pair-trading`, `leveraged-trading`, etc.). The inline comment explaining why it exists: *"Prompt rule enforced deterministically: small distiller models keep emitting style/methodology narratives despite the instruction."* That's real, current-code evidence that the small Cerebras model (`gpt-oss-120b`) doesn't reliably follow this specific prompt rule — the concrete reason Claude is worth testing here specifically, distinct from every other Cerebras-direct job in the cluster.

## The plan itself (delivered in full to the user in-chat; summarized here with code references)

**Architecture — how the CLI would be invoked.** Reuse `apps/context/src/claude/claude-code.client.ts` (on `feat/basket-hetzner-migration`, not `apps/agent`, not yet shared) rather than building a new invocation wrapper. It already does exactly what this job needs: `spawn()` with `-p --output-format json --no-session-persistence --json-schema <schema> --max-turns <n> --model <model> <prompt-as-last-arg>`, stdin ignored, auth via the host's own `claude login` state (not a repo env var) — which means **this only works on a host with a persistent, already-authenticated service user (Hetzner), never Railway**. Since interest-distiller's own Hetzner cutover (PR #791) also hasn't happened, this makes that cutover a hard prerequisite for the CLI-swap question, not a parallel independent track. Recommend extracting `ClaudeCodeClient` into a shared package before a second consumer forks it.

**Structured output — simpler than first assumed.** The right reference pattern is `ClaudeCodeClient.runStructuredWithMeta()` (`--json-schema` + `structured_output` field + zod `safeParse`), already proven end-to-end for basket generation — not `extractEqlConditions()`'s markdown-fence regex scrape (`apps/agent/src/signals/trigger-manager.service.ts:112-136`), which is solving a different problem (parsing prose out of Elfa's Builder Chat, not a CLI you control the output contract of). `InterestDistillerOutputSchema` (`apps/agent/src/ai/background/interest-distiller.agent.ts:16-44`) would need conversion to JSON Schema for the `--json-schema` flag — verify what conversion utility the basket path already uses before assuming a library.

**Real measurement, not the reasoned estimate above.** Use the existing `--user-id=<id>` one-shot flag (`main-interest-distiller.ts`, added in PR #791) to run 10-20 real single-user calls through `ClaudeCodeClient.runStructuredWithMeta`, and read the numbers straight off its already-returned `ClaudeRunMeta` — `duration_ms`, token counts, and **`total_cost_usd`** (the CLI's own dollar-equivalent cost accounting per run, even under subscription billing). This directly answers Step 1's "needs its own volume/sustainability math" ask, and is the one piece of this plan cheap enough to run before any Hetzner-dependency investment — no branch merge required, just a spike script and a Claude Max login on any box.

**Offline quality eval.** Closest in-repo precedent is `apps/agent/test/background-eval.ts` (+ fixtures) — real background-agent functions run against hand-authored evidence-object fixtures, deterministic `expect` checks plus an LLM-judge pass. Directly reusable shape for interest-distiller's `InterestEvidence` (`memory`, `personaLine`, `journalLines`, `watchedHandles`). The single cleanest deterministic A/B metric between Cerebras and Claude: run `isStyleTopic()` violation rate on both models' output over the same fixture set.

**Env/secrets.** `interest-distiller-runner.module.ts` (PR #791) already uses a bare `ConfigModule.forRoot()`, no Zod validation — the same footgun class as the already-flagged `SIGNAL_ADAPTIVE_POLICY` default-divergence issue (see Step 5 job 5). A CLI-based version adds a second, worse failure mode on top: auth isn't an env var at all, it's host-level `claude login` state, which no schema check can catch — needs a pre-flight `claude --version`/auth probe in the runner, not just careful env defaults.

**Risks specific to this path:** dependency on an unmerged sibling branch (`feat/basket-hetzner-migration`) for the reusable client; Hetzner-only auth model; per-invocation CLI process overhead at low-hundreds-of-users/night volume, unmeasured against the current serial-loop design's "order-of-seconds per user is fine" assumption; shared-window contention with made-baskets is currently *unmeasurable*, not "comfortable," since neither job's Claude-CLI path is in production yet; no programmatic Claude Max window/session-limit signal, only the indirect `total_cost_usd`/latency-degradation proxy.

**Go/no-go read given to the user:** worth testing, not worth committing to. Run the 10-20-call real measurement (§ above) first — cheap, fast, doesn't need either unmerged branch to land — and let those numbers plus the offline quality comparison decide whether the bigger Hetzner-dependency investment is justified. Don't size capacity or write a cutover runbook before that data exists.

## Update — 2026-09-16 (spike run + results + decision)

the §"real measurement" and §"offline quality eval" steps above are now RUN (they were designed-only before). full report with tables + example triggers: [Interest-Distiller: Claude CLI vs Cerebras — Step 7 Spike Results](https://app.notion.com/p/Interest-Distiller-Claude-CLI-vs-Cerebras-Step-7-Spike-Results-3dd4641ea90c8124938ef26b507c846e). throwaway scripts on branch `feat/interest-distiller-claude-cli-spike` (pushed, no PR): `apps/agent/src/scripts/interest-distiller-claude-spike.ts` (cost/latency) and `interest-distiller-quality-ab.ts` (quality A/B + neutral judge). read-only, 15 real dev users, reused the same evidence + prompt the prod job builds.

**cost/latency (opus, clean run):** $0.048/user/night mean, 20s median / 30s p95 latency, 100% schema-valid (needs `--max-turns` >= 2, a 1-turn cap aborts structured output). opus cheaper AND faster than sonnet (sonnet writes ~2.5x more tokens). cerebras baseline is far cheaper (flat plan, or metered gpt-oss-120b ~$0.001-0.002/call; exact plan NOT verified), so the swap adds recurring cost and saves none. latency, not cost, is the real constraint at scale (serial loop vs the 04:00 window + made-baskets session contention).

**quality:** isStyleTopic violations cerebras ~2-3%, claude 0%. neutral blind judge (grok-4.3) over 15 users: overall a TIE (opus 6 / crb 6), cerebras MORE grounded (8-3), claude slightly better watch phrasing (7-5). eyeballing the text: opus writes genuinely better triggers (tailored thresholds, real catalysts, pair/basket aware) but occasionally invents a theme; cerebras is formulaic (2% move + RSI/bollinger boilerplate) but stays grounded.

**pipeline finding (confirmed by tracing code):** distiller openThreads -> `followUpHook` -> `trigger-synthesizer` -> `trigger-manager` -> `elfa.createQuery` (api.elfa.ai). so the distiller output really does arm Elfa. BUT `isPairStatStatement` gates pair/ratio/z-score statements: the personal watch path swaps them for a generic template, the ghost path routes them to the `pear-stat-rs` local stat rail (not shipped/armed). opus loads most of its better triggers with ratio legs, so on the personal path its wording is templated before Elfa. net: the pipeline already neutralizes opus's main differentiator.

**decision (2026-09-16): NO-GO for now.** not "claude is worse", it is "blocked on the pipeline": opus's ratio-heavy edge only pays off once `pear-stat-rs` ships and the personal path routes to it. revisit and re-test on FIRED triggers then (cerebras-nudged-toward-ratios vs opus). don't commit to the CLI/hetzner path before the rail. cost + latency + ops (hetzner-only auth, unmerged-branch dep) stay against it regardless.

**real defect found (separate from the model question):** `persistOpenThreads` runs `normalizeLooseInterestTopic`, which does NOT call `isStyleTopic`, so style-topic open threads reach the `followUpHook` watch set unfiltered (unlike interest tags, which `normalizeInterests` filters). a ~3 line guard closes it, model-independent. tracked in Current Focus Open Loops.

## Update — 2026-09-22 (pear-stat-rs status + exact pipeline wiring gap, verified live via `gh` + code)

Checked whether `pear-stat-rs` has shipped, since that's what the NO-GO is gated on. Answer is split, and more specific than "not shipped":

- **The API binary IS live in production** — `pear-protocol/pear-stat-rs`, deployed on Railway (`https://pear-stat-rs.up.railway.app`), and `agent-pear-v2` already defaults `STATS_BASE_URL` there (`apps/agent/src/config/app.config.ts:50`) for basket-stats fetches and the Claude/quant MCP tool. This has been true for a while, unrelated to this spike.
- **The batch ENGINE cutover (replacing the TS stats cron) is still not confirmed done.** The repo's own `GO-LIVE.md`, read live 2026-09-22: hardening items are checked off (contract pin, coverage gate, singleton guard, watchdog), but §6 "Cutover discipline" is still an unchecked box — "Run in shadow mode first... this checklist covers deploy-readiness, not the shadow→cutover validation gate." So the engine side of "the rail" isn't confirmed live yet, independent of the API already answering queries.
- **The real finding: none of this matters yet for interest-distiller, because nothing in `agent-pear-v2`'s signal code calls pear-stat-rs at all.** Traced every `isPairStatStatement` usage in `apps/agent/src/signals/trigger-synthesizer.service.ts` and `apps/agent/src/ai/background/ghost-synthesis.processor.ts` — every single one is defensive (detect-and-template-away), never a call out to pear-stat-rs to evaluate a ratio/z-score. Two separate templating points, not one:
  1. **Personal watch path** (`trigger-synthesizer.service.ts:159-167`, `synthesizeSpecs`): `authored && !isPairStatStatement(authored) ? authored : template` — opus's pair-stat wording is discarded here. This was the one the original Notion report named.
  2. **Ghost path — partially preserved, then re-templated one step later.** `synthesizeGhostSet` (`trigger-synthesizer.service.ts:225-238`) actually DOES keep `authored` verbatim for ghosts (no `isPairStatStatement` filter there) and just tags `kindHint: "deterministic"` — this matches the "ghost path keeps the statement" framing from the original spike. But **the previously-undocumented gap**: if that ghost later gets merged into a cross-user "commons" cluster by `ghost-synthesis.processor.ts` (`authorStatement`, lines 360-407), the merge step templates it away too (`isPairStatStatement(statement) ? topicTemplate : statement`, same for the LLM-authored merge outcome). So a ghost's ratio wording only survives if it's never clustered with others — narrower survival than "the ghost path preserves it."
  3. Also confirmed: the `eql` field stored alongside a pair-stat ghost (`{ conditions: candidate.entry.conditions }`) is the ordinary single-asset Elfa condition, not a structured ratio/z-score spec — there is currently no machine-checkable representation of "SP500/BTC ratio > 2σ" anywhere, only the free-text `statement`. `kindHint: "deterministic"` is consumed today only by `ghost-report.ts`'s fire-projection analytics, not by any evaluator.

**Net: "revisit when the rail ships" undersold the gap.** Even a fully cut-over pear-stat-rs engine doesn't get opus's triggers firing by itself — there is no evaluator anywhere that polls or subscribes to pear-stat-rs and fires a pair-stat ghost/personal trigger. That's new code, not a config flip. See the reply given in-chat 2026-09-22 for the concrete pipeline-change list (structured condition capture at synthesis time, a stat-rail evaluator alongside `ghost-shadow`, un-gating the personal-watch template branch, a `DeterministicSignalCondition`-shaped measurement contract so `SignalDispatchService` composes it like an Elfa fire, and picking push (`stats_done` `pg_notify`) vs poll for the trigger cadence).

## Update — 2026-09-22 (research-augmented variant considered and declined — reasoned, not measured)

Asked in-chat whether harnessing Claude's live research (`WebSearch`/`WebFetch`, the made-baskets pattern) — instead of the plain tool-free structured-output call the spike actually tested — would change the NO-GO. No spike was run for this variant; this is a reasoned projection, not a measurement, and is recorded as such.

**The case for it:** the spike's own tool-free run showed opus already writes better-tailored triggers than cerebras (real catalysts, concrete thresholds) but with a specific flaw the neutral judge penalized it for — "occasionally invents a theme." Live research is the natural fix for exactly that flaw (grounding, not a general quality lift).

**Why it was declined anyway:**
- Upside is narrow (closes a groundedness gap) not broad — doesn't change the tie-ish overall judge result into a clear win.
- Cost/latency go materially worse, not marginally: made-baskets' research stage is the expensive/slow leg of its 3-Opus-call pipeline (~$2.18/basket all-in); interest-distiller runs per-active-user nightly with unbounded growth — reopens exactly the volume/sustainability risk Step 1 flagged and this spike deliberately avoided by testing a tool-free call.
- Doesn't touch the separate, already-identified blocker: `isPairStatStatement` templates ratio/pair-stat wording away before Elfa regardless of how it was authored — research-grounded or not.

**Decision (2026-09-22):** don't pursue the research-augmented variant. Marginal quality upside doesn't clear the cost/latency bar even before running the numbers. Extends, does not overturn, the 2026-09-16 NO-GO. If this is ever revisited, the cheap next step (not yet done) would be the same 10-20-user spike design with `CLAUDE_TOOLS=WebSearch,WebFetch` enabled, judged specifically on groundedness — but there's no current plan to run it.
