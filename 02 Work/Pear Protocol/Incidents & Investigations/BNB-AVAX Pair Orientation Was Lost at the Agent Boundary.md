# BNB/AVAX Pair Orientation Was Lost at the Agent Boundary

## Symptom

In a production Agent Pear chat, the user asked:

> Is it a good time to trade BNB/AVAX

The stats tool returned a canonical `AVAX/BNB` row with `rollZ +2.35`, where positive means AVAX was rich versus BNB. The first answer preserved that meaning. After the user challenged the convention, a later answer re-expressed the same data as `BNB/AVAX = -2.35` and said BNB was cheap versus AVAX.

A separate Agent Pear UI screenshot also showed `BNB / AVAX` beside `Rolling Z-score 2.35`. That is a frontend orientation-display risk, but it is not the runtime path that produced the chat's negative number.

## Scope and verdict

**Chat verdict:** the backend/statistics call did not produce the negative value, and the frontend did not transform the chat text. The first `-2.35` was generated by the pair-agent LLM after it manually invented an inverse-ratio sign flip.

**Primary enabling defect:** the pair-stats tool exposed the requested trade direction and the canonical statistical orientation in free prose, without structural fields connecting them. The pair node and composer therefore had to infer orientation from labels.

**Separate frontend finding:** the frontend contains a real orientation-safety problem in two UI paths. It can display requested long/short labels alongside a canonical signed score without carrying the score's `asset1/asset2` orientation. This was recorded as separate display-contract risk; frontend issue `pear-protocol/frontend#907` was opened in the wrong repository and closed. It was not the cause of the chat `-2.35`.


   It then output `-2.35`, `-0.84`, and `-0.01`.

6. The advanced final response at `14:19:52.364Z` repeated those negative values. The negative value was therefore born in the pair-node generation, not in the stats tool, frontend, or final text renderer.

## Runtime path


The chat did not call the frontend `/api/pair-stats` route or `mapPairStats()`.

## Backend and tool code evidence

### Order-agnostic lookup returns stored row order

`QuantService.getPairStats()` queries both orientations:

- `packages/shared/src/services/quant.service.ts:90-160`
- SQL at lines `105-115` matches either `(asset1=$1, asset2=$2)` or the reverse.
- The selected row retains its stored `asset1_id` and `asset2_id`; the query does not rewrite the row into the caller's order.

### Tool contract separates requested direction from canonical rows only in prose

`apps/agent/src/ai/tools/quant/pair-stats.tool.ts`:

- Lines `11-24`: `assetA` is documented as the user-convention first/long leg and `assetB` as the short leg.
- Lines `31-43`: the tool resolves those inputs and calls `QuantService.getPairStats()`.
- Lines `48-58`: comments say the z-score is canonical and must not be flipped.
- Lines `74-85`: `buildRow()` copies the stored asset IDs and signed values.
- Lines `103-152`: `formatPairStats()` prints `Long BNB / Short AVAX` in the header but prints the stored canonical `AVAXUSDT-BNBUSDT` row underneath.

The output does not contain structural fields such as `requestedPair`, `canonicalPair`, `richAsset`, `cheapAsset`, or `spreadOrientation`. Those semantics are carried in English sentences and are therefore vulnerable to LLM reinterpretation.

### Canonical context is flattened before composition

`apps/agent/src/ai/dag/builders/context-assembler.service.ts:4-10` extracts only `f.pair?.text?.trim()` for the pair section. Lines `90-117` assemble that text into the composer context. The composer does not receive a structured pair-stat object that it can copy without inference.

The pair agent itself is wired through `apps/agent/src/ai/agents/quant/pair/agent.ts:55-77` and invokes the model at lines `114-136` with `quant_pair_stats` as a tool.

## Why the model's inverse-sign explanation was wrong

The model asserted that the z-score was calculated on an invertible `Asset1 / Asset2` ratio. The repository's quantitative semantics say otherwise:

- `packages/shared/knowledge/quant/spread-and-z-score.txt:6` defines the spread as `price(A) − beta × price(B)`.
- `packages/shared/knowledge/quant/spread-and-z-score.txt:55` says the score is stored against a fixed canonical ordering and that swapping UI legs does not flip the sign.
- `packages/shared/knowledge/quant/trader-faq.txt:51-53` gives the same rule and explains that a reverse regression would be a different model, not a sign-flipped copy.

The model violated the tool's explicit “report verbatim, do NOT flip” instruction, but the instruction was not structural enough to prevent it from reframing the operation as a coordinate change.

## Separate frontend finding

The exact chat trace did not pass through frontend code. However, source inspection found two independent UI paths with the same orientation hazard.

### Base pair-stats path

- `apps/base-app/src/hooks/usePairTradingStats.ts:34-58` sends the requested long/short order as `asset1`/`asset2` to `/api/pair-stats`.
- `apps/base-app/src/app/api/pair-stats/route.ts:63-95` detects reversed upstream IDs and swaps IDs and weights.
- The same mapper copies `roll_zscore` at line `74` and does not transform it in the reversal branch at lines `85-92`.
- `apps/base-app/src/components/trade/BasketInfoSheet.tsx:241-269` renders `data.roll_zscore` while labeling weights with the requested long/short symbols.

### Agent Pear Live Signals path

The screenshot is from a separate path, not `mapPairStats()`:

- `apps/pear-web/src/routes/agent-pear.tsx:81-82` loads live signals.
- `apps/pear-web/src/hooks/use-agent-pear-signals.ts:41-65` fetches and normalizes them.
- `apps/pear-web/src/server/agent-pear.ts:61-73` calls the active-signals API.
- `apps/pear-web/src/lib/agent-pear-normalizers.ts:95-104` maps `long_asset`/`short_asset` to display labels and copies `viable_signal.roll_zscore`.
- `apps/pear-web/src/components/agent-pear/signal-card.tsx:38-65` renders the pair labels and lines `90-94` render the score.

No sign inversion was found before or after either path. The frontend issue is therefore a display-contract/orientation mismatch, not proven causation for the chat response and not a justification for blindly applying `z *= -1`.

## Final causal verdict

```text
Backend negative z-score:       disproved
Frontend transformed chat sign: disproved
Another stats call returned it: disproved
LLM manually reinterpreted it:   confirmed
Tool/architecture enabled it:   confirmed
Separate FE display risk:       confirmed
```

The first origin of the negative number was pair-agent generation `3a06b358dddcb9da`, after the second tool call had again returned canonical `+2.35`.

## Correct contract direction

The orientation boundary should be deterministic and structural. A pair-stat result should carry, at minimum:

```text
requestedPair
canonicalPair
asset1 / asset2
rollZ
spreadDefinition
richAsset / cheapAsset
quantOptimalDirection
```

Consumers should copy the canonical signed score with its canonical pair, or display the requested trade direction separately. They should not infer rich/cheap from the user-entered pair label and should not assume that reversing the legs means negating the existing score.

## Disposition

- No production code was changed during this investigation.
- Frontend issue `pear-protocol/frontend#907` was closed because it was opened in the wrong repository.
- The related Sep 16 work-log finding about orientation-dependent pair statistics remains relevant: [[16th Sep 2026]].
- This report is the durable record for the exact production trace and the corrected separation between the chat root cause and the separate frontend display risk.
