- **Second run failed on a real script bug**, first time the admin's "removed linebreaks" attempt at a key fix actually got SSH auth working: `mkdir: cannot create directory '/run/agent-pear': Permission denied` — `scripts/hetzner/deploy.sh` created its run dir as plain `prakh`, but `/run` is root-owned tmpfs. Confirmed on the box: dir didn't exist, `prakh` has passwordless sudo. Fixed in PR #809 (`sudo install -d -o prakh -g prakh`), merged.
- **Third run failed on a second real bug**, further downstream: `sh: 1: pnpm: not found` inside `railway:prisma:generate`, which shells out to a bare `pnpm -C packages/database run generate:all`. The script's top-level calls used `$PNPM_BIN`/`$NODE_BIN` by absolute nvm path, but nothing put that dir on `PATH` for nested subprocess calls — a non-interactive SSH session never sources the profile nvm normally sets `PATH` from, so the nested call fell back to the box's system Node v18 with no `pnpm` on `PATH` at all. Fixed in PR #810 (`export PATH="$(dirname "$PNPM_BIN"):$PATH"`), merged.
- **Fourth run succeeded clean end to end** — [run 35435058033](https://github.com/pear-protocol/agent-pear-v2/actions/runs/35435058033): HEAD fast-forwarded, deps installed, Prisma generated, `shared`/`context`/`indexing`/`agent` built, `daemon-reload` ran, reported "deploy complete." ## BNB/AVAX pair-orientation investigation — exact production trace

Full write-up: [[Incidents & Investigations/BNB-AVAX Pair Orientation Was Lost at the Agent Boundary]].

- Rechecked the exact US Langfuse session `26a170e0-d10a-4fd9-a721-dbffb1f3a298`, initial trace `8ba9a091239d8dd69aa2006547763bfc`, and challenge trace `e9ab24a66325ef8178ee37e479c1b0c4` rather than relying on the earlier frontend hypothesis.
- Both `quant_pair_stats` calls returned the same canonical rows: `AVAXUSDT-BNBUSDT`, 1h `rollZ +2.35`, with the tool explicitly saying the values were canonical and must be reported verbatim. The first pair response preserved `+2.35` and correctly described AVAX as rich versus BNB.
- The first negative value appeared in pair-node generation `3a06b358dddcb9da` at `2026-09-18T14:19:28.338Z`, after the user challenged the sign. The model invented an inverse-ratio sign flip and produced `-2.35`; no frontend route or mapper was in this chat path. Chat root cause: loss of canonical/requested orientation in an unstructured tool contract, followed by LLM reinterpretation—not a frontend transformation.
- The frontend does contain a separate orientation-safety risk: `mapPairStats()` and the Agent Pear signal normalizer can present requested long/short labels alongside an unchanged canonical score. This is a display-contract concern, not the cause of the chat's `-2.35`, and no frontend issue remains open (`pear-protocol/frontend#907` was closed because it was opened in the wrong repository).
- Correct durable rule: do not blindly negate the score when legs are swapped. Carry canonical pair, requested pair, spread orientation, and rich/cheap fields structurally so downstream agents and UI do not infer semantics from labels.
