## Fixed: ratio / weighted-ratio TRIGGER & LADDER opens always failed validation

- **Report (verified in Langfuse):** every `open_position` call with a `ratio` or `weighted_ratio` condition failed with errors like `Invalid condition: expected string, received undefined`. The model guessed field names (`symbol`, then `symbolA`/`symbolB`) and retried up to 11 times in one turn. Users were then told false things: a "please confirm" for a trigger that was never staged (`7e74054c7106eb2b01ce1e1d3b2f9c97`), "Pear only executes at market price" (`ea8bd6b98f5231b89f4921f5517b3082`), and "basket orders aren't supported" (`4d46e9d1ebf28a2560804b8c795e6fe4`).
- **Root cause (confirmed in code):** the tool's `condition` description only said `...type fields` with a single `price` example, and `parseConditionArg` joined only `issue.message`, dropping `issue.path`, so the error never named the field.
- The trade-execution node prompt does list the fields. The only other `open_position` caller found is advanced/direct mode, which doesn't get that prompt. Whether the failing traces ran in advanced mode is **not yet confirmed**.
- **Fix:** listed the fields for each condition type in the description, and prefixed each error with its path (`condition.symbol_a: …`). Spec updated, plus a new `ratio` case. 99/99 pass, agent `tsc` clean.
- Commit `a78b6bd7` on `fix/open-position-condition-fields`. **PR #1017** → `development`, open, CI pending.
- This is a follow-up to [[TRIGGER-LADDER JSON Crash Silently Substituted the User's Trade]].

### Weekly sentiment failed from Hetzner → fixed in PR #1034

- **Error:** `prisma.assetSentiment.updateMany(): Transaction API error: Transaction not found`, after ~9 min of LLM work on 184 stale assets. The whole write rolled back.
- **Root cause (strong evidence):** `ingestAssetRun`/`ingestCategoryRun` do one `updateMany` per row inside one interactive `$transaction`, which has Prisma's 5 s default timeout. Measured TCP connect VPS → `viaduct.proxy.rlwy.net` ≈ 30 ms, so ~175 rows exceeds 5 s. Daily runs (~15 rows) fit. On Railway's private network the same code takes well under a second, which is why it never failed there. Per-query time inside Prisma was estimated, not measured.
- **Fix:** `{ timeout: 60_000, maxWait: 5_000 }` on both ingest transactions (same pattern as `conversation-store.service.ts`). [PR #1034](https://github.com/pear-protocol/agent-pear-v2/pull/1034), commit `64ae34f7`, branched from `main` `33c5bee6`. The user pushed it and merged it **to `main`** (17:09 UTC, `2765c164`). The Hetzner deploy workflow succeeded, and the weekly re-run then exited 0.
- `development` does not have it yet: back-merge `main → development` is pending.
