## SL/TP hallucination investigation (read-only, no code changed)

- Investigated a Discord-reported recurrence ("Blackie | Rysk": *"it is hallucinating tps and sls now"*) against a specific production session (`a6045423-d7e1-47df-95e3-722fc9e10374`) via Langfuse trace/observation reads.
- Found the agent surfaced two different unrequested TP/SL figures (a 7.5%/12% code-attached default, then a stale remembered 15%/15% preference) within minutes, after the user had explicitly said "no sl no tp."
- Tested the user's hypothesis that a same-day Gemma→GPT-OSS-120B model swap (Cerebras retired `gemma-4-31b`, hotfixed composer/modeClassifier/reaction/scheduler onto GPT-OSS ~2.5h before the incident) was the cause. Git-archaeology showed neither node actually producing the bad output (planner, tradeExecution) had recently switched models. Live-replayed the exact captured production context against the real models: tradeExecution's `skipRisk` omission was 8/8 deterministic (context bug, not model noise); planner's GPT-OSS-120B hallucinated the stale memory 3/5 times only once the instruction had rolled out of context, 0/5 when it was still visible.
- Root cause: `skipRisk` is pure LLM-context state with no structural persistence, a 3-turn raw history window on the tradeExecution node, a recall-summary refresh that's cumulative across a TG session that never rotates daily (confirmed stale on the very first message of the day), and a memory-precedence rule that exists only as prompt text at three independent injection sites, never enforced in code.
- No fix implemented this session — recommended promoting risk-protection intent to structured, server-persisted trade-flow state. See [[Stale Recall Memory and an Unpersisted skipRisk Flag Resurfaced Old TP-SL Preferences]].
- Separately confirmed: `ap-api` has a real `DELETE /sessions/:sessionId` endpoint (ownership-checked, hard-deletes the session + cascades messages) — but this repo doesn't contain the web frontend, so whether ap-web actually surfaces a "clear history" UI for it is unconfirmed from this repo.

## TG session audit + Kalshi routing investigation (read-only, no code changed)

- Ad hoc requested review of another real production TG DM session (`telegram:1789835514`, @ClBlockchain) via Langfuse — 293 turns over 30 days, zero ERROR/WARNING-level observations.
- Observed but did not root-cause (noted here, not written up as a standalone incident — insufficient depth of investigation to date): the agent gave a confident, detailed "Robinhood Chain mainnet launched July 1 2026, Lighter deeply integrated" answer eight days after correctly telling the same user it had no verified information that Robinhood had a blockchain at all — a likely hallucination, not independently traced to a specific tool call. Also observed ~5 days of the bot incorrectly telling the user Lighter wasn't supported before correctly confirming a linked Lighter account, consistent with a feature rollout the earlier turns hadn't caught up to.
- Deep-dived one concrete failure: a Kalshi "odds on the Fed rate" query returned a bare refusal after the immediately preceding turn (same topic) had routed and answered correctly. Traced via trace diffing (ruled out model/provider/prompt-version/context differences — all confirmed identical) plus a full planner/DAG code read. Found two confirmed, separable root-cause layers: (1) the `research` node's own trigger text both includes ("macro updates") and excludes ("NOT for live price") this exact query shape, and redirects to `marketScanner`, which doesn't cover Kalshi by its own definition either — a genuine routing dead zone; (2) independent of why, the DAG has no contract enforcement rejecting an all-null/`generalChat:false`/`clarify:null` planner decision — the system's own existing fallback for "nothing to route" (`createDefaultPlan()`) is wired only to a missing/invalid planner response, not to this structurally-valid-but-empty one.
- Not proven: whether the trigger-text conflict is actually what drove this specific LLM sample (no live reproduction performed; temperature 0.1 isn't fully deterministic; only one occurrence observed). No fix implemented. See [[Kalshi Odds Query Fell Into a Planner Routing Dead Zone With No Empty-Plan Fallback]].
