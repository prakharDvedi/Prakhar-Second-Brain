## Found and fixed a stale "sequential on purpose" bottleneck (~3h → ~1h)

- A real dry-run log (hyperliquid) showed the per-basket cost breakdown: category-sentiment ~116s, research ~247s, selection ~20s ≈ 383s/basket. At ~10 baskets/platform × 3 platforms, that's the ~3-hour full run the user flagged as unacceptable.
- `refreshDaily` ran all 3 platforms sequentially across all 3 passes (general/equity/directional), with a comment claiming "Sequential on purpose — the runs share the LLM + stats API budget."
- Spawned an investigation agent to check whether that comment reflected a real constraint. Findings: the comment predates `categoryAnalysisCache` (git blame: commit `7489385e`, June 2026, before the cache existed); the cache is explicitly built for concurrency (memoizes the in-flight Promise, not the resolved value, so concurrent identical queries dedupe onto one call); `CLAUDE_MAX_BUDGET_USD` is enforced per-subprocess by the Claude CLI itself, not tracked in-process; no semaphore/lock/pool anywhere in the subprocess spawner. Nothing shared would actually break under concurrency.
- Changed the 3 sequential platform `for` loops to `Promise.all` in `apps/context/src/sentiment/services/made-baskets-cron.service.ts`. Verified `tsc --noEmit` clean and the full context suite (15/15, 98/98) before and after a follow-up comment trim (feedback: the first version of the added comment was bloated, re-explaining implementation detail the code already shows).
- Committed as a single squashed commit, opened [PR #796](https://github.com/pear-protocol/agent-pear-v2/pull/796) against `development`, user merged it same day.
- **Not yet confirmed live** — expected ~3h → ~1h wall-clock, but the code has not actually run a full multi-platform pass yet (see below).
