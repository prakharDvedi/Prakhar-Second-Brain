## Basket-stats hotfix — split categories vs basket-stats service URLs (PR #677 → main, #678 → development)

- Root-caused a production `MadeBaskets` cron failure: `context`'s single `STATS_BASE_URL` fed two consumers on two different services — `AssetUniverseProvider` → `GET /categories` (`pear-pair-signals`) and `QuantService.getBasketStats()` → `POST /stats/basket` (`pear-stat-rs`). The Aug 27 change (`11a29155`) collapsed both onto the categories host, so `/stats/basket` 404'd; baskets still persisted but with null stat columns, and the cron raised a misleading `No baskets generated` alert. See [[One Service URL Fed Two Different Services, Nulling Basket Stats]].
- Fix: introduced `CATEGORIES_BASE_URL` for `/categories`, restored `STATS_BASE_URL` to `pear-stat-rs` for `/stats/basket`. `context` `AssetUniverseProvider` reads the new var; `QuantService.getBasketStats()` keeps `STATS_BASE_URL`. `indexing` (only a `/categories` consumer) had its var renamed `STATS_BASE_URL` → `CATEGORIES_BASE_URL`. Both URL vars moved to `z.url()`. Env templates + READMEs updated.
- Verified this session: `tsc --noEmit` clean (context + indexing); tokenomist-index spec passing; live route probes (`GET /categories` 200 pair-signals / 404 stat-rs; `POST /stats/basket` 404 pair-signals / 401 then 201 stat-rs with a valid multi-leg body + key).
- Shipped as an emergency hotfix directly to `main` (PR #677, merged ~06:25 UTC). Because a prod fix must re-level the branches, opened PR #678 (`fix/split-stats-service-urls` → `development`) as a clean cherry-pick of the same commit — open, in review.
- Railway (owner-applied, values not read by me): `context-app` had `STATS_BASE_URL` set explicitly (the real live cause — the code default alone couldn't override it) plus `CATEGORIES_BASE_URL` added; `indexing-prod` got `CATEGORIES_BASE_URL` (its old `STATS_BASE_URL` now dead). Confirmed via CLI (names only) both prod vars present and both services redeployed SUCCESS @ ~06:32 UTC, all 8 prod services Online.
- Checked the development environment too: `indexing` and `ap-worker` have neither var set → they ride the correct `z.url()` code defaults, and there is no `context` service in dev. So **dev needs zero var changes** — the prod bug existed only because prod carried an explicit `STATS_BASE_URL` override; dev never did.
