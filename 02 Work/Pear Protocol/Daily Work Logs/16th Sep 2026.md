## Fixed the P1 Redis leak found in review on #757 and #758

- Separate session/thread, same day: reviewed whether comments were "dropped" on 4 open PRs (#757, #758, #725, #786) — checked REST issue-comments, REST inline-review comments, and GraphQL `isMinimized`; nothing was hidden, all comments accounted for.
- Root cause on #757/#758's shared P1: `TwitterModule`/`SentimentModule`/`StatsModule` (`apps/context`) and `AssetIndexModule`/`CoinIndexModule`/`TokenomistIndexModule` (`apps/indexing`) each declared their own `RedisProvider` in their own `providers` array — 4 and 3 separate ioredis clients respectively, silently. `main.ts`'s existing single `redis.quit()` in each app only ever closed one, so a systemd-run one-shot logged completion, then hung until timeout-killed (confirmed against real 12 Sep VPS logs the reviewer cited).
- This corrected an earlier note ([[Harness Integration/Step 3 — Tokenomist + OI Canaries on Hetzner]], 2026-09-12) that had marked this exact hang "Confirmed fixed" after the #748/#753 `redis.quit()` change — that fix addressed the two Redis tokens known at the time, not the per-module duplication nobody had noticed.
- Fix: added a shared `RedisModule` (`packages/shared/src/providers/redis.module.ts`) — a Nest module class is a true app-wide singleton even when several feature modules import it, unlike a provider literal repeated per module. Switched every affected module to `imports: [RedisModule]` instead of redeclaring the provider. `main.ts` needed no changes in either app.
- Added `redis-module-wiring.spec.ts` in both apps as a regression guard; sanity-checked it actually fails if the regression is reintroduced.
- Verified: `tsc --noEmit` clean both apps; full suites pass (`apps/context` 11/57, up from 10/54; `apps/indexing` 4/37, up from 3/34).
